# Issue 636: turn billing usage is not request pressure

## Source audit

Read together with [issue 634's measured-floor report](issue-634-proven-floor.md). No reporter databases or session files were opened; the four supplied assistant-usage rows and logs are the reproduction evidence.

1. **MC does not sum assistant messages into the pressure numerator.** `packages/pi-plugin/src/index.ts:2809-2825` passes one `event.message` to `persistPiPressureFromMessageEnd`; `pi-pressure.ts:95-116,150-172` extracts that message's usage and adds its input/cache components, excluding output. The only normalization is the existing smaller `totalTokens - output` reading for older inclusive-cache APIs. `index.ts:901` replaces `lastInputTokens`, not adds to it. Pressure snapshots take the maximum of persisted and live readings, not their sum (`pi-pressure.ts:188-240`). Cumulative billing fields are not the historian's pressure numerator.

2. **The OMP Cursor provider really returns turn-level usage on one assistant message.** Audited upstream **v18.8.3**, [packages/ai/src/providers/cursor.ts](https://github.com/can1357/oh-my-pi/blob/v18.8.3/packages/ai/src/providers/cursor.ts): `streamCursorWithWireMode:1028-1046` creates one assistant output; `:1319-1389` dispatches interaction/exec frames throughout the server-owned turn; `:1461-1475` waits for tool dispatches and emits that single completed message. `applyTurnEndedUsage:5387-5411` explicitly adopts the authoritative *per-turn* counters from `TurnEndedUpdate`, subtracts cache input from inclusive input, and assigns their sum plus output to `totalTokens`. Thus MC receives the aggregate already present on the message; it does not create it. We cannot independently establish the reporter's exact inner API-request/tool-round count from the supplied table, but a 6,525,247 input reading cannot measure one request on the pinned 256,000 wall.

3. **Both reclaim and historian used that same poisoned measurement.** `context-handler.ts:3493-3496` passes the admitted input to the pipeline and `:6541` passes it as `currentTotalInputTokens` to emergency reclaim. Shared `packages/plugin/src/hooks/magic-context/emergency-drop.ts:223-226` computes `fixedFloor = max(currentTotalInputTokens - tailTokens, 0)`. The logged 6,485,845 is consistent with 6,525,247 minus 39,402 measured tail tokens, not an independent capacity measurement. The historian formerly resolved the same persisted/live pressure again. It now receives the transform's admitted pair (`context-handler.ts:3590-3593,4863-4865,4906-4920`). Shared `compartment-trigger.ts:639-663` compares its percentage with the force band. 6,525,247 / 224,000 produces the logged 2913.1%.

4. **OpenCode records step usage, not the OMP Cursor turn.** Audited upstream [OpenCode v1.17.11 session/processor.ts:693-729](https://github.com/anomalyco/opencode/blob/v1.17.11/packages/opencode/src/session/processor.ts#L693-L729): `step-finish` passes `value.usage` to `Session.getUsage`, assigns `assistantMessage.tokens = usage.tokens` (only *cost* accumulates), and stores the step-finish tokens. Its v2 bridge publishes the same step tokens and resets the assistant step id. MC TS consumes the single row's input/cache components at `packages/plugin/src/hooks/magic-context/event-handler.ts:814-817`; v2 reads the latest assistant at `v2/hooks/context.ts:1045,1106` and `usage-reading.ts:61-62`. Rust receives the host's resolved input unchanged (`rust-mode-transform.ts:1171-1173,2508`). There is no cross-message numerator sum in these paths. A malformed provider *step* payload could still reach TS/Rust; per-step storage is not a universal validation fence. There is no evidence here of the OMP server-owned Cursor loop being used by OpenCode, so this repair is Pi-scoped, not a change to OpenCode's accepted-pressure contract or Rust's algorithm.

## Admission and fallback

- The numerator's admission wall is the **raw absolute window**, not the output-reserved 224k percentage denominator. A normalized provider input larger than a provider/overlay/detected wall is rejected, not clamped to a fake 100%+ emergency (`pi-pressure.ts:43-49,133-148`). Input exactly at the wall and input above the soft reserve but within the wall remain valid. Old inclusive-cache normalization still prevents double counting.
- With no authoritative wall (including advisory catalog metadata), the explicit ceiling is **3,000,000 input tokens**. This is the existing OpenCode model-resolver sanity ceiling (`packages/plugin/src/shared/models-dev-cache.ts:56-63`), conservatively above the ordinary million-token measurements, including 634's 757,872 and 1,328,370. An unknown-window 6.5M billing counter is not capacity proof. This is an admission policy, not a claim that all future models physically stop at 3M: an authoritative larger wall can admit larger requests. Aggregates below this ceiling cannot be recognized from size alone without a trusted window.
- `index.ts:741-776,850-935` rejects the record for pressure and floor updates, logs `provider_usage_not_single_request` once per session, and uses a sane host reading if available. It cannot invalidate a detected cap with rejected usage. When the host also lacks a usable reading, pressure is left unknown until the context pass can count request messages.
- `context-handler.ts:3109-3164` tokenizes the current request view, using read-only last-served-prefix replay when available so prior reductions are not counted as raw history again, plus the current system/tool envelope when available. Incomplete host envelope metadata leaves a messages-only estimate, not manufactured provider proof. Sanitization also rejects old persisted numerators and the anomalous t3 host `contextTokens=703,152` (`pi-pressure.ts:358-402`). The same admitted pair feeds execute, emergency, tiered reclaim and the historian.
- `pi-proven-floor.ts:47-88,238-274` uses the same admission wall during legacy-history repair and rechecks even a marked measured floor against it. Footer/status and transform/historian consumers supply the wall **before** applying any floor. No migration is added and tokenizer estimates never prove capacity. 634's catalog repair, failed-response rejection, model attribution and token-threshold override remain intact.

## What this does not change

At an 80% execute threshold, the force band is still **85%**, from `packages/plugin/src/shared/escalation-bands.ts:10-17`. A genuine 211,039 / 224,000 = 94.2% reading therefore still executes and may legitimately fire `force_band`; rejecting 2913% does not require forcing it into the ordinary historian path. Pi's emergency uses the separately resolved hard wall. The legacy `times_execute_threshold_reached` field has no runtime increment in these paths, as established in the 634 audit; its zero is not proof that normal scheduling did not execute. Neither telemetry semantics nor threshold precedence is changed here.

The older tests that required above-window usage to count in full or be clamped were changed explicitly: those assertions contradicted request-size admission and reproduced this phantom emergency. Their below-wall emergency controls and explicit provider-overflow recovery pressure remain covered.
