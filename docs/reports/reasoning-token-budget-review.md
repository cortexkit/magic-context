## Findings

### 1. Blocker — the budget mutates thinking inside the active Anthropic turn (630 conflict)

**Trigger:** one real user request followed by three assistant/tool steps, with no intervening user request; `keep_reasoning_tokens: 0` on an already-authorized rebuild. The newest step is exempt, but the two preceding steps of the *same active turn* are selected/emptied. Both ordinary and prefix-bound selection admit this.

**Locations:** `packages/plugin/src/hooks/magic-context/reasoning-budget.ts:190-196` exempts only newest/latest replayable assistants; `reasoning-removal.ts:168-179` accepts earlier active-turn steps. Pi has the same exemption at `packages/pi-plugin/src/reasoning-replay-pi.ts:185-204`, then applies the result at `:417-440`. Rust's equivalent exemption is `crates/mc-module/src/transform/reasoning_budget.rs:30-54`. The design explicitly rejects whole-turn protection at `docs/designs/reasoning-token-budget.md:494-496`.

**Failing tests written:**

- `review: issue 630 leaves all thinking in the active Anthropic turn unchanged`: expected `[]`, received `["a", "b"]` from TS selection.
- `review: issue 630 leaves all thinking in the active Anthropic turn unchanged in Pi`: expected original signed thinking bytes, received empty thinking with signatures removed for a0/a1.

**Attribution:** deliberate 620 policy, incompatible with the supplied parallel 630 rule. The pre-existing proactive binding strip also explicitly includes the newest open tool round (`packages/pi-plugin/src/provider-error-recovery-pi.ts:244-269`); changing just the new cutoff does not reconcile every thinking mutation lane. These tests are future-contract conflict witnesses, not claims that the candidate violates its own old active-turn policy. Coordinate first-selection eligibility across budget, inline, merged-assistant, native and proactive/recovery paths. Do not enforce the new protection by simply withholding old frozen clears on a defer: that would restore signed bytes and violate the replay contract.

### 2. Blocker — frozen removals are not absorbing when a removed assistant becomes exempt

**Trigger:** a rebuild removes assistant A while B is newest. A later host subset, undo or changed visible lineage leaves A as the newest replayable assistant. Whole-part replay now skips A and re-shows its original signed reasoning, despite its id remaining in the saved removed set. No new budget selection is necessary. A similar exception exists in merged-assistant replay. Rust suspends an existing clear on an exemption-changing priced pass and serves the original signed block again.

**Locations:** `packages/plugin/src/hooks/magic-context/reasoning-removal.ts:194-206` recomputes the current exempt message during every replay; `strip-content.ts:925-935` skips exact frozen merged-part decisions for that message. Rust explicitly implements restoration in `crates/mc-module/src/transform/reasoning_clear.rs:36-57` by setting `newest-assistant-keep`; `:208-234` then stops replaying the clear.

**Regression witnesses (TS failures executed; Rust witness not compiled or run):**

- `review: a saved removal never restores signed thinking when its message becomes exempt`: the expected served tool-only array receives the original reasoning plus `sig-a` again (Vertex-shaped history).
- `review: a frozen merged-assistant strip never restores thinking on a host subset`: the frozen empty sentinel is replaced by raw thinking on a canonical-Anthropic subset.
- Rust witness `review_reasoning_clear_never_restores_a_frozen_block_on_exemption_change` — **written, not compiled or run**. It calls Rust replay before and after the exemption refresh, not just the persisted-id reader. Exact filter: `cargo test -p mc-module --lib review_reasoning_clear_never_restores_a_frozen_block_on_exemption_change -- --nocapture`. Expected failure: the JSON after refresh contains original `thinking-old` / `signature-old`, whereas the before value contains empty reasoning with no signature.

**Attribution:** inherited, not newly introduced by token selection. The existing test `replay skips the newest assistant with replayable content, as Rust does` documents the opposite policy. The design's “nothing comes back” assertion is therefore stronger than the lanes it reuses. A scalar budget increase alone does not cause this restoration; visibility/exemption changes do. Restoration changes a shared message's bytes, and reappearance/re-removal can also change defer bytes. These unit witnesses prove the restoration; they do not claim a live 400 for a particular undo sequence. Preserve historical removal decisions or explicitly settle this exception before claiming unconditional absorbing replay.

### 3. Should-fix — OpenCode tag estimates are attributed to the wrong assistant step

**Trigger:** consecutive reasoning/tool steps with `info.tokens.reasoning: 0`; A has a large thought and B/C have short thoughts. Give the budget exactly the sum of the three actual plaintext estimates. Pi fits all three; TS using persisted tool estimates selects a cutoff of 1 instead of 0 and unnecessarily removes A.

**Locations:** the new adapter sums reasoning estimates by tag *owner* in `packages/plugin/src/features/magic-context/storage-tags.ts:708-728` and prefers that sum in `reasoning-budget.ts:206-223`. But existing tag semantics are not one reasoning estimate per owner: `tag-messages.ts:941-987` assigns a tool tag **precedingThinkingParts**, updated at `:1079`, not that tool owner's own thought. Parallel tools repeat that association. A text tag separately stores its own message's thought at `:872-882`, so mixed text/tool histories can also add estimates with different provenance.

**Failing test written:** `review: stored tool estimates charge each assistant's own reasoning exactly once`. It uses the real `tagMessages`, real in-memory schema and real `getReasoningTokenEstimatesByMessage`, not fabricated golden costs. Expected cutoff 0; received 1. Passing control `review control: Pi charges each step's own plaintext once` uses the same plaintext sizes and budget.

**Attribution:** introduced by treating historical tag accounting as step accounting. Stored estimates can shift a large old cost onto a newer step, duplicate it, or undercount that newer step. This is especially relevant to routes without reported reasoning, not routes with positive reported usage (which bypass the estimate). Correct the ownership/deduplication or fall back to the actual host step's text when the stored provenance does not prove its own group cost. The shared numerical golden is insufficient to prove adapter parity.

### 4. Should-fix — TS bust selection omits calibration for fallback and inline estimates

**Trigger:** an Opus-family session with frozen `proseRatio > 1`, old/missing reasoning token columns (or inline thinking), and no reported reasoning usage. Three raw text estimates fit the supplied budget, but two calibrated estimates do not. The real postprocess path keeps all three instead of removing the two older steps.

**Locations:** `packages/plugin/src/hooks/magic-context/transform-postprocess-phase.ts:2592-2605` supplies a calibrated *stored* estimate map but never supplies `proseRatio` to `opencodeReasoningBudgetCutoff`. Consequently fallback text and inline text use 1 in `reasoning-budget.ts:222-226`. Pi passes session calibration at `packages/pi-plugin/src/context-handler.ts:6693-6694`; Rust uses model calibration at `crates/mc-module/src/transform/reasoning_budget.rs:106-121`. Status/projection also receive a ratio, so they can disagree with the actual TS selection.

**Failing test written:** `review: bust selection applies frozen prose calibration to unstored thinking estimates`. It freezes the actual Opus 5.5 calibration via `sessionDecisionCalibration` and runs `runPostTransformPhase`. Expected saved removals `{assistant-0, assistant-1}`; received an empty set. No new private configuration schema or fake ratio is used.

**Attribution:** introduced. Pass the same frozen calibration used for the persisted estimate to both live fallback and inline costing. This matters on upgrade for NULL estimate rows even when the new config key is omitted.

### 5. Should-fix — already-frozen merged-assistant reasoning still consumes the TS budget

**Trigger:** canonical Anthropic, three consecutive assistant steps; a prior rebuild froze the middle step's merged-reasoning strip. Retained first/newest steps cost 100 each; the already-off-wire middle step reports 20,000. A later rebuild with a 200-token budget clears the retained first step and advances the watermark to 3, although the actual kept reasoning already fits.

**Locations:** `packages/plugin/src/hooks/magic-context/transform-postprocess-phase.ts:2582-2605` recognizes whole-part removed ids and binding-recovery ids, but not ordinary merged-part frozen decisions. Those decisions are read/replayed only at `:3660-3705` / `strip-content.ts:925-935`, after budget costing. Rust's cost adapter includes `strip:merged_reasoning:` in the gone set at `crates/mc-module/src/transform/reasoning_budget.rs:32-41`.

**Failing test written:** `review: merged-assistant frozen strips cost zero on the next budget rebuild`. It creates real merged-part decisions with `findMergedReasoningStripDecisions`, persists them through `addMergedReasoningStrippedIds`, then executes real postprocess. Expected watermark 0; received 3.

**Attribution:** introduced. Costs must describe the representation actually replayed, not raw host reasoning that a frozen serializer repair already removes. Part-level decisions can leave a sibling thinking block, so blindly treating every bare merged id as whole-step gone is also wrong. Account for the exact frozen part selection before computing the kept cost, without applying new strips on defers.

### 6. Should-fix — Rust module fallback does not use TS/Pi's canonical-first provider aliases

**Trigger:** module-side config resolution (no host-resolved effective value), with `{"openai/*":250,"openai-codex/*":500,"google/*":750}`. For `openai-codex/gpt-6.1-sol`, TS/Pi resolve 250; Rust resolves 500. A canonical-only `google/*` override for `google-antigravity/gemini-3.8-flash` falls through in Rust rather than resolving 750.

**Locations:** `crates/mc-module/src/config.rs:268-294` reuses the Rust cache-TTL resolver, which checks only the literal provider at `:354-382`. The shared TS resolver explicitly tries canonical/native provider aliases at `packages/plugin/src/shared/prompt-surface.ts:89-109`, via `shared/harness-provider-map.ts:110-119`. Host-resolved effective budgets at `crates/mc-module/src/lib.rs:10329-10335` hide this mismatch for current OpenCode senders, but older senders/autonomous module resolution do not.

**Rust witness — written, not compiled or run:** `review_reasoning_budget_aliases_follow_the_shared_canonical_first_lookup`. Exact filter: `cargo test -p mc-module --lib review_reasoning_budget_aliases_follow_the_shared_canonical_first_lookup -- --nocapture`. Expected first assertion failure: actual 500 versus expected 250. The second assertion expects 750 for Google's alias (source predicts 10,000), but cannot be reached if the first assertion fails. Passing TS control: `review control: TS aliases resolve canonical provider wildcards first` (250 and 750).

**Attribution:** introduced reuse of a pre-existing resolver asymmetry for the new setting. Exact/base/wildcard/default lookups on ordinary canonical provider ids are covered and work; this finding is specifically about known alias parity, not a claim that all per-model resolution is broken.

### 7. Note — positive reported usage with an empty non-opaque summary diverges in Rust

**Trigger:** three typed reasoning steps, each reporting 100, with empty summary text, no signature and no native metadata; budget 200. TS's adapter charges the positive reported count and returns cutoff 2. Rust's source computes no cutoff because it rejects the empty body before it reads reported usage.

**Locations:** `crates/mc-module/src/transform/reasoning_budget.rs:99-110` returns 0 for an empty text/opaque/inline group and only then reads `/info/tokens/reasoning`. TS uses declared typed-part presence at `packages/plugin/src/hooks/magic-context/reasoning-budget.ts:203-224` and gives the positive report precedence.

**Rust witness — written, not compiled or run:** `review_reasoning_budget_reported_count_survives_an_empty_summary`. Exact filter: `cargo test -p mc-module --lib review_reasoning_budget_reported_count_survives_an_empty_summary -- --nocapture`. Expected assertion failure: actual cutoff 0 versus expected 2. Passing TS control: `review control: TS uses positive reported costs even with an empty summary`.

**Attribution:** introduced adapter discrepancy. This is synthetic coverage, not evidence that a real provider bills for an empty unencrypted item. If the wire adapter drops it entirely, charging zero may be preferable, but then TS and the stated reported-cost rule need the same interpretation. Do not equate this with the encrypted-empty-summary case: native encrypted metadata is recognized by the Rust source; the ordinary opaque 1,000-token TS control passes, but no Rust control ran in this review.
