CK session extensibility: providers, preflight and a runner that freezes

An explainer of design draft r3.1, for the operator. Nothing described here is built yet. Each section cites the design section it summarises; where this page simplifies, the cited section has the full rule. Anything marked illustrative is a sketch made for this page (screen wording, example layouts), not something the design specifies.

The question it answers: how modules such as AFT and Magic Context contribute to a model session that a CortexKit runner executes, under two constraints [§1]:

  • the runner knows nothing about personas, session kinds or any module's internals;
  • the prompt cache is never broken by accident.

1. The roles

Five principles carry the design [§2]:

  1. The caller decides, the runner executes, providers supply.
  2. Broca never sees a persona, a session class or a turn's origin. It gets a flat manifest of providers and what they contribute.
  3. The prefix is frozen. System text and tools are resolved once and replayed byte for byte. They change only through an explicit change applied under a declared policy.
  4. Every module output that affects bytes is written when it's produced. Resume replays the record and never asks a module to produce it again.
  5. Each provider keeps itself coherent. It returns a finished, self-consistent contribution. The engine doesn't compose, filter or repair it.

Prefrontal: the caller

Owns the persona. Decides what a session gets, runs preflight, checks the persona's requirements, sends Broca the session manifest, and later decides when a change is applied. Desktop and phone talk to Prefrontal, never to Broca directly [§2, §4, §11.3].

Broca: the runner

Runs the session from the manifest it was given, freezes it, writes everything byte-affecting to its WAL, places cache breakpoints, and applies changes when told. Thalamus is a second runner on the same interface [§1, §2, §7, §12.1].

Providers: the modules

A module may play several of the four kinds below. It declares them in its provides list, which Prefrontal reads from the catalog without calling anything [§3, §4.2].

KindSuppliesExampleDeclared as
ToolProvidertool definitions; executes the callsAFT; Magic Context's ctx_* toolsck.provider.tool/v1
SystemPromptProvidersystem textMagic Context's desk guidance (full or light); Prefrontal's own persona and role textck.provider.system-prompt/v1
CompactionProviderthe shape of the history sent to the modelMagic Context; a classic summarise-and-continue engineck.provider.compaction/v1
StepTransformProviderwrite-time changes to the newest messageMagic Context's tags, reminders and per-turn recallck.provider.step-transform/v1

A session has at most one CompactionProvider. Without one, history is sent as written, and a request that no longer fits the window fails with the model provider's own overflow error [§3].

2.1 The persona and its params

The persona belongs to Prefrontal. It decides which tools the session needs, how strict it is about them, and which params to ask each provider for. CK defines a small shared vocabulary; a provider may add axes of its own. A value a provider doesn't know is refused at preflight, never guessed [§4.1].

ParamValues
behaviorautonomous | interactive
scoperead | readwrite | all (every tool provider serves all)
tool_descsconcise | full
excludetool names

The final list is still open (design §16.3).

2.2 Preflight

preflight(cwd, params) returns a manifest: the exact tool definitions and system text the provider would put on the wire, a digest for each item, and one digest over the whole manifest [§4.2].

  • Pure. It binds nothing, starts no watcher, builds no index and writes nothing, so Prefrontal can run it while planning, before it creates a worktree or spends a model call.
  • Its own route. It's served as an internal_service target {module_id, service_id: "preflight"}. The module ignores the bound root there; cwd travels as the call argument. There is one long-lived preflight route per (provider, trust value), never one per candidate worktree. After launch, the session uses the normal bound route.
  • Trust comes from the route, never from a param. Prefrontal stamps a trust fact when it opens a provider route; the daemon relays it, and it's frozen for the life of the route. Providers that narrow on trust are listed in the daemon's admission_facts_targets. For preflight on the shared service route, a trust claim may instead travel with the call; the provider accepts it only when the route's daemon-stamped principal is Reserved{prefrontal-core}, and otherwise treats the call as untrusted. An untrusted route narrows what the provider returns.
  • Each provider resolves its own configuration (user, project and harness tiers) with its own merge rules. There is no second merger.
  • Coherent. Everything the returned tools and text refer to is in the manifest. With bash_status disabled, AFT returns a foreground-only bash whose replies never hand back a task.
  • Deterministic. Same inputs, same bytes: stable key order, no timestamps, counters or random ids. The digests depend on it.
  • Bytes only. Settings that don't change bytes (watch timeouts, size caps) aren't in the manifest; they travel with each tool call.
  • Bounded by the caller. Prefrontal caches manifests by (module, cwd, params, trust), gives each preflight a short deadline, and on a timeout keeps the last good manifest and retries later. A turn is never delayed by preflight.

2.3 System text is operator authority

A SystemPromptProvider is one the operator chose to install. Its text may vary with params and user-level configuration, but it never includes content supplied by a project: a cloned repository must not be able to inject text into the system prompt. A project-level setting may only choose among texts the provider ships. Per-project and per-session content (project docs, memories, counts) goes into user-role content produced by the compaction provider [§4.3]. Who carries project docs is still open; see section 12 of this page.

2.4 The persona check and the session manifest

Each role declares, per provider, its params, its required tools (by model-facing name) and whether it's strict or lenient. If a required tool is missing, a strict persona fails with a typed launch refusal naming the tool, before any worktree exists; a lenient one runs without it [§4.4].

Prefrontal then sends Broca the session manifest [§4.5]:

  • the tool providers, each with its params and manifest;
  • the system-prompt providers in order (order is precedence), with Prefrontal first: its persona and role text is preflighted and digested like any other, and a persona catalog update is a change like any other (section 6 of this page);
  • the compaction provider, or none;
  • the step-transform providers, in order.

Broca freezes it on RunStarted.

2.5 Compaction setup

If there is a compaction provider, Broca calls its setup once when the session starts. It returns [§5.1]:

  • The initial CompactionMessage, so the session starts with its head in place. For Magic Context this inserts m0 and m1 before the first user message: an empty range replaced by [m0, m1].
  • Message stability: a rank for each of the provider's own messages, higher meaning it changes less often. Magic Context's main sessions declare {m[0]: 2, m[1]: 1}; a subagent session has no m0 or m1 and declares nothing. The indexes refer to the provider's output, not to positions on the wire.

3. One model step

On every model step, Broca sends the compaction provider a status and waits for one of four answers [§5.2].

3.1 What the status carries

  • the step id, and whether the step is a new user turn or a tool step;
  • the model and variant, and the resolved context window and output limit;
  • the previous response's usage (input, cache read, cache write, output), its real completion time and finish reason;
  • the previous attempt's provider error, if any (an overflow, for example);
  • Broca's estimate of the request about to go out, labelled as an estimate (Broca has no tokenizer for most model families), plus the previous step's measured input;
  • prefix_rebuilding with its reason (flush, manifest change, model switch, expired cache), set when this step's prefix is being rebuilt anyway;
  • the id of the newest message written and of the last CompactionMessage applied;
  • the current time.

3.2 The four answers

AnswerMeaningWhat Broca does
NOOPNothing changes. No bust.Sends with the CompactionMessage already in force (if any) and the raw tail.
CompactionMessage{range: {from, to}, replacement: [messages], bust: soft | hard}. An unlabelled one counts as hard.Runs the structural checks (section 4 of this page). If they pass, it writes the message to the WAL and sends with it; it stays in force until another replaces it. If they fail, it refuses the message, records that, and proceeds with the previous CompactionMessage.
WAIT{reason, bound_ms}: hold this step while the provider compacts.Sends nothing to the model, enters the recorded compaction_wait state, publishes a status, and asks again when the provider says it's ready or bound_ms runs out (section 7 of this page).
REFUSE{code, reason, retryable}: fail this step.Sends nothing and ends the run with the terminal reason CompactionRefused{provider, code, reason} (section 7 of this page).
no answer in timeThe call has a budget of about 2 s for NOOP and CompactionMessage.Proceeds with the last recorded CompactionMessage, which is always a valid state, and records the timeout.

A pending change waiting for a bust (section 6 of this page) is applied at the step whose CompactionMessage carries the matching label [§11.2].

4. The CompactionMessage picture

A CompactionMessage names a range of the transcript by Broca's durable message ids (never array indexes) and gives the messages that stand in for it [§5.3]:

  • from is the marker. Messages before it aren't sent.
  • to is exclusive: the start of the provider's protected tail. Messages from to onward go out raw. to may not separate a tool call from its result.
  • The replacement stands in for the range. For Magic Context it's [m0, m1, reshaped messages from the range]. It's the provider's finished output, so the step-transform hooks don't run over it.
  • It always describes the whole working range, never a delta. ctx_reduce only queues drops; they land on the provider's next pass as a new replacement with the marker unchanged.

4.1 Checks before sending

Broca verifies every CompactionMessage before it sends it [§5.3]:

  • roles follow the model family's rules;
  • every tool call is paired with its result, checked across the replacement and the raw tail together;
  • no tool-call id appears that isn't in the range;
  • kept signed thinking is byte-identical.

A view that fails is refused and recorded, and Broca proceeds with the previous CompactionMessage.

System appends are never compacted. When a range covers a mid-conversation system message (a change applied by append, section 6 of this page), Broca re-emits each one byte for byte, in order, right after the replacement: that's the “system appends” box in Figure 3. Editing or removing a sent system message would invalidate the cache from that point (and, on Fable 5.1 and Opus 5.5, the thinking in every later assistant turn), so a replacement that would drop one is refused like a structural failure.

Written to the WAL. Every CompactionMessage is a record, and resume replays the latest one. If the provider is down, Broca keeps serving the last recorded compaction plus the raw tail; the remaining risk is overflow, which Broca detects from usage.

5. The four hooks on a turn

Step-transform providers change messages when they are written, not every time history is sent [§6.1].

HookMay changeTypical use
PreUserthe user message or noticetags, recall appended as a block, reminder wrapping
PostAssistantthe text of existing text blocks only; never blocks, tool calls, thinking or signaturestags, trailing-blank cleanup
PreToolwhat executes: pass, a rewritten input, or a refusal whose text becomes the tool result. The recorded assistant message keeps what the model produced.the dropped-input guard
PostToolthe tool resulta tag prefix, the Channel 1 reminder, a size cap

One frame

PreUser before RunStarted or the notice record; PostAssistant before ModelStepFinished; PreTool before ToolDispatchIntent (which records the input that will actually run, so at-most-once execution holds); PostTool before ToolResult [§6.2].

Attribution

Broca stores the original and the final value in full, plus one entry per stage: {module, note, digest of its output}. The note is short and written by the module (“prefixed tag”). A UI diffs original against final itself and lists the notes; the protocol has no diff format [§6.2].

result_integrity: append_only

A tool may declare it. PostTool may then prepend or append blocks but never change existing lines. AFT's read needs this, because a later edit addresses its hashline tags. Broca rejects and records a hook output that breaks the declaration [§6.2].

Order, budget, failure

Several providers on one hook run in manifest order, each getting the previous one's output. Each declares a per-hook time budget, capped engine-wide. A hook that fails or times out passes the message through unchanged, and Broca records that [§6.2].

PostAssistant and the display

The display lane has already streamed the original text; subscribers get the final version on the control lane. Editing text next to signed thinking is accepted by Anthropic today; a live test in the build still confirms it [§6.2].

Reading history

Providers see new messages through the hooks. session.read(from, to) returns any range with each message's raw and final form (after a restart, for the provider's own history work, to recover originals). Providers tell wakes from nudges themselves; Broca doesn't classify turns [§6.2].

6. Changes while a session runs

The prefix is frozen, so a changed configuration never leaks in by itself. Detection and application are separate steps [§11].

Config changesa file the provider watches
→
Hint (optional)ck.ext.changed.<module_id> on NATS, where a bus exists
→
Re-preflighton the hint, and at every turn start and task start
→
Digest comparetop-level digest equal: nothing to do
→
New manifest + policysent to Broca, pending
→
Appliedat the policy's moment; manifest_applied written

6.1 Detection

  • Watch set. Providers watch the global configuration plus the configuration of every root that has a live route now (the daemon answers supervisor.live_roots). A missing file is watched through its nearest existing parent. Roots that were only preflighted aren't watched; turn-start re-preflight covers them [§11.1].
  • The hint. The provider publishes {scope, generation, boot_id}, with no content. The module id comes from the bus credential, never the payload, so one provider can't send hints in another's name. scope is the entorhinal project id, never a path.
  • Correctness never depends on the bus. A public install may have none; Prefrontal re-preflights at every turn start and task start anyway, so a missed hint only delays detection.

6.2 The four policies

If the top-level digest differs, Prefrontal sends Broca the new manifest with one policy. The choice is Prefrontal's, per class: masons and readers default to next_prefix_rebuild (short-lived, never worth a bust); heads default to next_soft_bust, with the pending change shown on the board and phone [§11.2].

PolicyApplied when
immediatelythe next step, including a tool step; the prefix is rebuilt
next_soft_bustthe next CompactionMessage labelled soft or hard
next_hard_bustthe next CompactionMessage labelled hard
next_prefix_rebuildthe next step whose prefix is dead anyway (an expired cache, a model switch)
  • What changed Broca works out from the per-item digests. It appends where the model family allows and rebuilds otherwise. An appended system message goes only right after a user turn (tool results count) and before an assistant turn, never between a tool call and its result, and it carries only operator text, never recall or tool output.
  • Recorded as manifest_applied{digest, policy, step}. On resume, the drift guard compares against the latest applied manifest, not the one the session started with.
  • A change that never finds its moment stays pending. Prefrontal can show it and flush.
  • Disabled tools take effect at once: until the change is applied, the provider refuses calls to a tool the user just disabled, with a clear reason. The policy only decides when the model stops seeing it [§11.4].

6.3 Flush and Apply Now

session.flush_prefix drops the frozen prefix and applies any pending manifest on the next step, whatever the policy. Apply Now is a Prefrontal op that calls it; Desktop and phone go through Prefrontal and never talk to Broca directly [§11.3].

7. WAIT and REFUSE: what the user sees

WAIT

  1. Broca holds the step, sends nothing to the model, and records the compaction_wait state.
  2. It asks again on compaction.ready(session) from the provider (the normal path: Magic Context's historian finishes, or a classic summary returns) or when bound_ms runs out.
  3. The provider may answer WAIT again, but an engine-wide cap limits the total wait per step.
  4. At the cap, Broca decides from its own numbers: if the request is estimated to fit the resolved window with the last recorded compaction, it sends; if not, the step ends as a refusal with code compaction_wait_exceeded. It never sends a request it knows will overflow.
  5. A WAIT cut by a daemon stop is sealed Interrupted like any run and continues only when the caller resends.

[§5.4]

REFUSE

  1. Broca doesn't send. It ends the run with CompactionRefused{provider, code, reason}, written to the WAL. Nothing is added to the model's history.
  2. Prefrontal gets it as the run's terminal result, like any other. reason is user-facing text and Prefrontal shows it.
  3. Retryability maps onto the existing transient or permanent classes. Transient: retrying automatically makes sense (the historian was only busy). Permanent: the user has to act (switch to a larger model, fix the configuration).
  4. The session stays usable; the next send asks the provider again. A refusal on a tool step keeps the tool results already written.

8. Resume: replay only

Frozen manifestplus every manifest_applied
+
The WALevery CompactionMessage, every hook output, any pending WAIT
→
Replayno provider is called to produce anything again
  • Resume replays the frozen manifest and the WAL; nothing is re-derived from a module [§8].
  • The drift guard compares against the latest applied manifest [§11.2].
  • A WAL reader that meets a record kind or value it doesn't understand refuses rather than skipping it. That must-understand gate ships, confirmed on the running Broca image, before anything writes the new records; after the first one is written, rolling Broca back below the gate is blocked [§13].

9. Thalamus and other runners

Thalamus is the runner for Claude Code sessions and uses the same provider interface. What differs is the runner: Claude Code owns its transcript and resends the whole message list on every request. So Thalamus keeps what Broca's WAL keeps (the hook outputs and the latest CompactionMessage), keyed by message identity using the ccm-N digest ids already agreed with THALAMUS, and applies them to each request. Claude Code's session.compact hook makes the marker real in Claude Code's own transcript. Magic Context's Claude Code-specific transform lane collapses into this interface [§12.1].

Adapters for OpenCode and Pi are possible on the same interface, keeping the record by message identity as Thalamus does, but they aren't in scope for the first build [§12.2].

10. Tool calls and notices, briefly

Tool calls

  • Each call carries the params the provider was preflighted with, so behaviour matches the frozen description.
  • Each call also carries a digest of the input schema it was described with, plus a semantics version. Description text isn't pinned. A provider refuses only when it can no longer honour that schema, with tool_revision_mismatch, which SDKs treat as terminal.
  • A setting that changes description bytes stays frozen until a change is applied; meanwhile the provider refuses by name any call the current config forbids.
  • Host-only arguments are rejected in calls from the model.

[§9]

provider_notice

  • Asynchronous events: AFT's finished background task, Magic Context's idle nudge. Sent with a per-event id.
  • Written as a user-role message tagged with its provenance, at the next legal position, never between a tool call and its result. It goes through PreUser and can later be compacted.
  • One engine-wide size cap; an oversized notice is refused back to the provider, never truncated.
  • Whether an idle session wakes for a notice is Prefrontal's decision.

12. Open items

Who carries project docs. System text may not include project content (design §4.3), yet heads get ARCHITECTURE.md and STRUCTURE.md there today. A session without a compaction provider needs a carrier; ALF proposes a frozen user-role block written with the first user turn (a PreUser output from Prefrontal). Magic Context's m0 also carries the docs today, so a head with both would get them twice. Exactly one of the two must own them [§16.1].
  1. A notice channel to the user, not the model, for Magic Context's toasts and status notices. Deliberately later, as a separate design.
  2. The final list for the shared param vocabulary.
  3. The schema of the trust fact, defined in the provider interface; the daemon relays it opaquely.
  4. The per-family table of append-only tool and system changes, from BROCA's renderers, and how Broca records the capability per session.
  5. The engine-wide caps, published as readable numbers: total WAIT per step, hook budgets, the notice size cap.
  6. Magic Context's in-memory state between passes: persisted, or served by one long-lived instance. Magic Context's own concern, not part of the protocol.
