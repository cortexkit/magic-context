# Rust shown-memory projection

The Rust renderer follows the operator redesign recorded in
`docs/designs/memory-s3-projection.md`. The retired algorithm rebuilt a session's
memory view from canonical rows while subtracting deferred operations; Rust no
longer uses that reconstruction. A SOFT refresh may rewrite the delta block
(m[1]) while keeping the baseline block (m[0]) and its image frozen. Its memory
bytes depend only on previously shown state and its own immutable agent fragments.
Automated and foreign writes wait for an independently required HARD rebuild.

## Ownership and rendering

The applied tuple is `ModuleMeta.memory_projection` in store.db. Its text manifest,
captured row revisions, immutable metadata, profile, processed fragment watermark,
committed full/marker/aggregate fragments and baseline hash commit with the frozen
text/image pair under the existing cache generation CAS. Store migration 69 fences
older binaries that would otherwise drop the new JSON field on a metadata rewrite.
It adds no second cache table or cross-database transaction. The move inventory
ships the opaque cache meta and preserves the context.db fragment IDs.

Canonical mutations and their pre-rendered fragments commit in context.db first.
Rust's fragment namespace is `ck-mc`; identical host session names cannot cause it
to consume a TypeScript fragment from another harness. Explicit search and the
one-time hint producer compare current complete prose with the shown manifest;
an old revision, cue, marker or unknown legacy manifest does not suppress a hit.
Failure to load a visibility manifest disables suppression.

SOFT preserves committed fragments, uses 25% of the configured memory text
budget for corrections (the same allowance as TS/Pi), a
40-full-line limit, reserved marker budget and final aggregate line. Memory updates
are excluded from the independent pressure calculation. A real HARD captures
canonical rows/revisions and the fragment watermark together, then resets the
fragment ledger. A marker-only HARD uses applied memory/profile and scores and
the frozen image. If independent content is unchanged, it commits markers only,
preserving the complete prior pair and its tuple. Same-revision external SQL prose
repair and workspace/privacy invalidations remain stronger safety inputs.

## Departures from the original campaign specification

- There is no adoption-class scan, projected live/deferred operation pool,
  A1/A2/A3 rebase, additive admission ledger, or hole-bearing mutation cursor.
  Neither foreign nor automated changes reach SOFT. Only own agent fragments do.
- Automated cue correction does not ride SOFT. An explicit own agent operation
  can show its full correction or a stale marker, even for an image-only memory;
  the frozen image is never regenerated by that SOFT.
- Search returns unlabelled current text, as TS/Pi do, not revision/adoption labels.
- The cached pair already owns its bytes and image. The projection binds that
  pair by its m0 hash rather than duplicating all bytes in a second snapshot table.
- Rust currently receives a capability-gated, pre-rendered mural from the host,
  without a source revision manifest. This slice freezes that artifact in marker
  probes and SOFT/defer. It cannot prove a host image and Rust-selected canonical
  text were produced from one cross-process read snapshot; adding such a host wire
  contract requires changes in the host TypeScript adapters, not just these Rust
  crates. Unknown cues never hide full text.
- Dashboard approval/undo routing remains in the dashboard slice. No dashboard
  epoch setter is introduced here. Rust agent operations keep existing mutation
  rows for compatibility; the SOFT renderer never reads those rows.

The shared golden is generated by the production TS/Pi composer and consumed by
Rust. It includes fixed-seed SOFT/defer/HARD sequences and exact full, marker and
aggregate bytes. Rust integration-level unit fixtures separately exercise cache
restart, CAS loss, marker-only versus natural HARD and canonical-search visibility.

## Pass labels and facade witnesses

`SOFT+` is the historical wire label for `PassPlan::Defer`, not for an authorized
SOFT refresh. A `ctx_memory` operation stores pre-rendered lines for its editing
session in the same transaction as the row change,
but it does not set refresh/force flags or open an m[1] SOFT by itself. The next
defer still replays the old bytes. At the next independently authorized SOFT,
the owning session appends the fragment; another session does not. A separately
requested `session.flush` is one such authorization and does not require HARD.

`facade_same_session_memory_edits_wait_for_an_independent_soft` uses the same
session cache keys for its token-resolved writer and transform routes. It checks
that the immediate SOFT+ defer retains cached bytes while the fragment is pending,
and that the following independently requested SOFT actually shows the edit.

`facade_memory_operations_match_ts_goldens_on_soft_and_isolate_sessions` calls the
real facade for update, merge, archive and additive save, then calls the real
`session.flush` dispatch and transform routes. Each resulting m[1] is compared
byte for byte with a fixed case generated by the production TS/Pi composer. It
also verifies that the other session's independent SOFT stays unchanged and that
both sessions replay their complete serialized outputs on the following defer.

`crates/mc-store/src/move_inventory.rs` records supported store version 69 and
classifies which data is exported with a session. The tuple is shipped through
the already-classified, session-owned `mc_cache_state.meta` column; fragment IDs
are exported unchanged. Their inventory declares collision refusal, but the
current module-half installer does not import Context entries. A populated
v68-to-v69 step-through test preserves old cache bytes, persists/reopens the tuple,
and confirms that a v68-only binary refuses the upgraded store.

## Open integration items

### HARD mural/text source coherence — owner: Rust parity slice S7

The mural/text source-revision check remains open in this Rust projection release.
A real HARD can currently combine newer canonical text
with an older host image. An opaque mural `content_hash` does not identify the
memory revisions that produced the image. The permanent
`review_hard_requires_mural_revision_coherence` witness stays ignored until S7
closes this host-manifest gap; it must not be weakened to accept mixed revisions.

The Rust parity slice (S7) must implement this host/Rust wire contract:

1. Whenever an enabled host mural supplies `data_url`, the host must also send
   `mural.source_manifest`: a versioned **memory source manifest** captured from
   the same read snapshot and tier
   selection that rendered that artifact. It binds the reader project and
   workspace membership, and identifies each source memory by
   `{project_path, memory_id, revision, content_sha256, cue_sha256}` (the cue hash is
   nullable). The manifest also binds the effective selection metadata, text/cue
   tier decision, policy/budgets and frozen expiry clock used for that selection.
   The host must persist and forward the manifest with its image bytes, not attach
   current row metadata to an older cached artifact. A compact source-revision
   token may replace the manifest only if it identifies that exact complete source
   snapshot; a project epoch, numeric ID watermark or image hash alone cannot.
2. Before committing or serving a new HARD tuple, Rust must validate the artifact
   identity and source manifest against the immutable memory source snapshot and
   tier decision used for that candidate's text. Missing, malformed or mismatched
   provenance is a source-mismatch refusal, not permission to mix sources.
3. On a mismatch, Rust rejects the candidate without advancing its cache
   generation, applied manifest, clocks or fragment watermark, and requests that
   the host re-render the mural from the agreed source snapshot. It may replay the
   prior complete tuple only where the existing recovery/privacy policy permits
   that fallback; a cold request without a safe prior tuple returns a retry/refusal
   rather than a mixed baseline. The regenerated artifact is validated again
   before adoption. A concurrent source change requires another capture/validation
   or safe replay, never a partial text/image commit.

This validation belongs only to an independently authorized HARD. It must not
create a HARD/SOFT opportunity, refresh flag, epoch bump or image regeneration on
an ordinary SOFT, defer or byte-identical marker-only commit.

### Context fragment-ID collisions — owner: agent-move campaign

`memory_agent_fragments` uses `PreserveOrRefuseCollision` because the applied
tuple's watermark and committed list refer to the exported integer IDs. The
current exporter preserves them and the module move preserves the tuple bytes.
The future **context-half importer** must enforce the collision policy before
making a complete move live. This is not an implemented end-to-end refusal
guarantee in S4, and integer remapping cannot be substituted without rewriting
every corresponding tuple reference atomically.

`context_fragment_collision_query_detects_foreign_id_without_reserving_or_writing`
exercises the same inventory-key query used by module preflight against an actual
destination Context fragment row: a foreign session owning the incoming ID is
detected as `key_collision`; an unused ID is the positive control. It checks that
the query writes no row, overwrites no foreign fragment and creates no reservation
or cache state. This is read-only collision-query coverage, not a context importer.
